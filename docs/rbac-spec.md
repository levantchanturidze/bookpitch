# Bookpitch — როლებისა და ნებართვების არქიტექტურა

**ვერსია:** 1.0
**ტიპი:** Multi-tenant SaaS (ჯავშნების პლატფორმა — კლინიკები, სალონები, სერვის-ბიზნესები)

---

## 1. მთავარი პრინციპი: ორი დამოუკიდებელი სიბრტყე

ყველაზე ხშირი არქიტექტურული შეცდომა ამ ტიპის პროდუქტებში — ერთი გრძელი წრფივი იერარქიის აშენებაა (`Super Admin > Admin > Owner > User > Executor`). ეს იმიტომ იშლება, რომ **პლატფორმის როლი და ორგანიზაციის როლი სხვადასხვა ღერძია** — ისინი ერთმანეთს არ აგრძელებენ.

```
┌─────────────────────────────────────────────────┐
│  PLATFORM PLANE — Bookpitch                      │
│  აკონტროლებს "კონტეინერს": ორგანიზაციებს,        │
│  ხელმოწერებს, ბილინგს, ინფრასტრუქტურას           │
│  SUPER_ADMIN · PLATFORM_ADMIN · SUPPORT          │
└─────────────────────────────────────────────────┘
                     ⇣ ქმნის / აჩერებს
┌─────────────────────────────────────────────────┐
│  ORGANIZATION PLANE — პარტნიორი ორგანიზაცია      │
│  აკონტროლებს "შიგთავსს": ჯავშნებს, კლიენტებს,    │
│  პერსონალს, ფინანსებს                            │
│  ORG_OWNER · ORG_ADMIN · BRANCH_MANAGER ·        │
│  FRONT_DESK · PROVIDER · ACCOUNTANT              │
└─────────────────────────────────────────────────┘
                     ⇣ ემსახურება
┌─────────────────────────────────────────────────┐
│  CONSUMER PLANE — საბოლოო კლიენტი                │
│  CLIENT (მხოლოდ საკუთარი მონაცემები)             │
└─────────────────────────────────────────────────┘
```

**კრიტიკული წესი:** პლატფორმის როლი **ავტომატურად არ იძლევა** წვდომას ორგანიზაციის მონაცემებზე — წვდომა ცალკე, ცხადი მოქმედებით მოიპოვება.

`SUPER_ADMIN` ამ წესის გამონაკლისია: **მას ტექნიკური ჭერი არ აქვს და ყველა ნებართვა უჭირავს.** ეს გააზრებული გადაწყვეტილებაა — სისტემა, სადაც რაღაც პრინციპულად შეუძლებელია, ვერ უმკლავდება რეალურ სიტუაციებს (Owner გარდაიცვალა, აკაუნტი ჩაიკეტა, მონაცემები დაზიანდა, სასამართლო მოთხოვნა შემოვიდა).

განსხვავება არა **უფლებაშია**, არამედ **პროცედურაში**: სენსიტიურ მონაცემებზე წვდომა ხდება break-glass რეჟიმით (თავი 7.2) — ძალაუფლება იგივეა, უბრალოდ კვალი რჩება.

## 2. სამი ცვლილება შენს თავდაპირველ სქემასთან

### 2.1. `Owner Admin`-ის გაყოფა ორად

ერთი როლი ორ სხვადასხვა პასუხისმგებლობას აერთიანებს:

| როლი | რას აკეთებს | რას **ვერ** აკეთებს |
|---|---|---|
| `ORG_OWNER` | იურიდიული მფლობელი. ბილინგი, ხელმოწერის გეგმა, ორგანიზაციის წაშლა, მფლობელობის გადაცემა | — |
| `ORG_ADMIN` | ყოველდღიური მართვა: პერსონალი, სერვისები, გრაფიკები, ფასები, რეპორტები | ბილინგი, ორგანიზაციის წაშლა, Owner-ის მოხსნა |

მიზეზი: მენეჯერს, რომელიც პერსონალს მართავს, არ უნდა შეეძლოს გამოწერის გაუქმება ან ბიზნესის წაშლა. ეს სტანდარტული გაყოფაა თითქმის ყველა B2B SaaS-ში.

### 2.2. `User` — ცუდი სახელია

`User` ეჯახება `users` ცხრილს და არაფერს ამბობს პასუხისმგებლობაზე. სწორია `FRONT_DESK` (ან `RECEPTIONIST`).

ასევე — რადგან პლატფორმა კლინიკებსაც ემსახურება და სალონებსაც, სახელები **ვერტიკალ-ნეიტრალური** უნდა იყოს:

| ❌ არ გამოიყენო | ✅ გამოიყენე |
|---|---|
| Doctor | `PROVIDER` |
| Patient | `CLIENT` |
| Procedure | `SERVICE` |

UI-ზე labels შეიძლება იყოს დინამიური ვერტიკალის მიხედვით (`clinic` → "პაციენტი", `salon` → "კლიენტი"), მაგრამ სქემაში ერთი სახელი უნდა იყოს.

### 2.3. ერთი მომხმარებელი ≠ ერთი როლი

ეს ყველაზე მნიშვნელოვანი გადაწყვეტილებაა და ახლა უნდა მიიღო, თორემ მერე მიგრაცია მტკივნეულია.

რეალური სცენარები, რომლებსაც წრფივი მოდელი ვერ ითავსებს:

1. **ექიმი, რომელიც ორ კლინიკაში მუშაობს** — კლინიკა A-ში `PROVIDER`, კლინიკა B-ში `PROVIDER`, სხვადასხვა გრაფიკით.
2. **სოლო პრაქტიკოსი** (ერთი სტომატოლოგი, ერთი სტილისტი) — ერთდროულად `ORG_OWNER` **და** `PROVIDER`. ეს ალბათ შენი მომხმარებლების უმეტესობა იქნება დასაწყისში.
3. **მფლობელი, რომელიც თვითონაც იღებს პაციენტს** — იგივე.
4. **რეცეფციონისტი, რომელიც ორ ფილიალშია** — `FRONT_DESK`, ორი branch-ის სქოუფით.

გამოსავალი: **membership მოდელი** — როლი არ ჯდება `users` ცხრილში, არამედ `user ↔ organization ↔ role` კავშირში.

## 3. მონაცემთა მოდელი

```sql
-- ვინ არის (გლობალური იდენტობა, ერთი ადამიანი = ერთი ჩანაწერი)
users (
  id, email UNIQUE, phone, password_hash,
  full_name, locale, mfa_enabled,
  status,                      -- active | locked | deleted
  platform_role_id NULL,       -- მხოლოდ Bookpitch-ის თანამშრომლებისთვის
  created_at, last_login_at
)

-- პარტნიორი ორგანიზაცია (tenant)
organizations (
  id, legal_name, brand_name, vertical,   -- clinic | salon | fitness | ...
  status,                                 -- trial | active | suspended | archived
  subscription_plan, owner_user_id,
  allow_support_impersonation BOOL DEFAULT false,   -- ← მნიშვნელოვანია
  created_at
)

branches (
  id, organization_id, name, address, timezone, status
)

-- ★ სისტემის გული: ვინ, სად, რა როლით
memberships (
  id, user_id, organization_id, role_id,
  status,                      -- invited | active | suspended | removed
  is_bookable BOOL,            -- ჩანს თუ არა კალენდარში როგორც შემსრულებელი
  invited_by_user_id, joined_at,
  UNIQUE (user_id, organization_id, role_id)
)

-- სქოუფი: რომელ ფილიალებზე ვრცელდება ეს membership
membership_branches (membership_id, branch_id)

-- როლები და ნებართვები = მონაცემი, არა კოდი
roles (
  id, key, display_name, plane,          -- platform | organization
  rank INT,                              -- იერარქიის შედარებისთვის
  organization_id NULL,                  -- NULL = სისტემური შაბლონი
  is_system BOOL
)

permissions (key, resource, action, scope, description)
role_permissions (role_id, permission_key)
```

### რატომ ასე

- `organization_id = NULL` როლებში → სისტემური შაბლონები. მოგვიანებით, როცა დიდ კლიენტს დასჭირდება custom role, უბრალოდ `organization_id`-ით შექმნი — **კოდის შეცვლის გარეშე**.
- `memberships` ცხრილი ხსნის ყველა ზემოთ ჩამოთვლილ სცენარს ერთდროულად.
- `allow_support_impersonation` — თითო ორგანიზაცია თვითონ წყვეტს, შეუძლია თუ არა Bookpitch-ის სუპორტს მის აკაუნტში შესვლა.

## 4. როლების სია

### 4.1. Platform Plane (Bookpitch)

| Key | Rank | ვინ არის | ძირითადი უფლებამოსილება |
|---|---|---|---|
| `SUPER_ADMIN` | 1000 | პლატფორმის მფლობელი | **ყველაფერი, ჭერის გარეშე** — platform-როლების დარიგება, feature flags, ტარიფები, გლობალური უსაფრთხოება + break-glass წვდომა ნებისმიერი ორგანიზაციის მონაცემზე |
| `PLATFORM_ADMIN` | 900 | Bookpitch-ის თანამშრომელი | ორგანიზაციების შექმნა/დაბლოკვა, ხელმოწერის მართვა, Owner-ის მოწვევა, პაროლის reset-ლინკის გაგზავნა, impersonation-ის დაწყება (თანხმობით) |
| `SUPPORT_AGENT` | 800 | სუპორტის ოპერატორი | **read-only** დიაგნოსტიკა: ორგანიზაციის კონფიგურაცია, ლოგები, ხელმოწერის სტატუსი. კლიენტების PII **დამალულია**. impersonation-ის მოთხოვნა შეუძლია, დაწყება — არა |
| `BILLING_MANAGER` | 850 | *(ოფციური)* ფინანსისტი | ინვოისები, ხელმოწერები, refund-ები. ჯავშნებზე/კლიენტებზე წვდომა არ აქვს |

> `SUPPORT_AGENT`-ის დამატება არჩევითია, მაგრამ **ძალიან რეკომენდებული**. სუპორტის 90% არ საჭიროებს წაშლის ან პაროლის reset-ის უფლებას; ცალკე read-only დონე დრამატულად ამცირებს blast radius-ს ჩაგდებული ანგარიშის შემთხვევაში.

### 4.2. Organization Plane (პარტნიორი)

| Key | Rank | ვინ არის | კომენტარი |
|---|---|---|---|
| `ORG_OWNER` | 100 | ორგანიზაციის მფლობელი | ბილინგი, გეგმა, წაშლა, მფლობელობის გადაცემა. ორგანიზაციას **ყოველთვის** უნდა ჰყავდეს ≥1 აქტიური Owner |
| `ORG_ADMIN` | 80 | მენეჯერი / ადმინისტრატორი | სრული ოპერაციული მართვა ბილინგის გარეშე |
| `BRANCH_MANAGER` | 60 | ფილიალის მენეჯერი | იგივე რაც Admin, ოღონდ `membership_branches`-ით შეზღუდული |
| `FRONT_DESK` | 40 | რეცეფციონისტი | ჯავშნები, კლიენტები, ჩეკინი, გადახდის მიღება |
| `PROVIDER` | 40 | ექიმი / სტილისტი / შემსრულებელი | საკუთარი კალენდარი, საკუთარი კლიენტები, საკუთარი ჩანაწერები და შემოსავალი |
| `SENIOR_PROVIDER` | 50 | *(ოფციური)* დეპარტამენტის ხელმძღვანელი | Provider + გუნდის კალენდრისა და ჩანაწერების ხედვა |
| `ACCOUNTANT` | 30 | ბუღალტერი | **read-only** ფინანსური რეპორტები და ექსპორტი. კალენდარზე/სამედიცინო მონაცემებზე წვდომა არ აქვს |
| `MARKETING` | 30 | *(ოფციური)* მარკეტერი | კამპანიები, პრომოკოდები, სეგმენტები. ფინანსებზე/კლინიკურ მონაცემებზე — არა |

> ⚠️ `FRONT_DESK` და `PROVIDER` **ერთსა და იმავე rank-ზე არიან, მაგრამ იერარქიულად არ არიან დაკავშირებული** — ისინი სხვადასხვა დომენში მუშაობენ. ეს იმას ნიშნავს, რომ როლების სისტემა **მესერია (lattice), არა ჯაჭვი**. ამიტომ "ვის ვის მართვა შეუძლია" ლოგიკა მხოლოდ rank-ის შედარებაზე არ უნდა აშენდე — გქონდეს ცხადი `can_manage_roles` სია თითო როლისთვის.

## 5. ნებართვების ნეიმინგი

ფორმატი: **`resource.action:scope`**

| Scope | მნიშვნელობა |
|---|---|
| `own` | მხოლოდ საკუთარი ჩანაწერები |
| `branch` | membership-ზე მიბმული ფილიალები |
| `org` | მთელი ორგანიზაცია |
| `platform` | გლობალური |

```
booking.create
```

## 6. ნებართვების მატრიცა

### 6.1. პლატფორმის დონე

## 7.1. Impersonation (სუპორტის წვდომა)

Bookpitch-ის თანამშრომელს დღეს თუ ხვალ დასჭირდება კლიენტის ეკრანის დანახვა. **არასოდეს გააკეთო ეს ბლანკეტური read-all უფლებით.** სწორი მოდელი:

1. **ორგანიზაციის მხრიდან ჩართვა** — `organizations.allow_support_impersonation` ველი. ზოგი კლიენტი (განსაკუთრებით სამედიცინო) კონტრაქტით მოითხოვს, რომ ეს გამორთული იყოს.
2. **მიზეზის სავალდებულო მითითება** — ticket ID + ტექსტი, ჟურნალში ინახება.
3. **დროში შეზღუდვა** — სესია ავტომატურად იხურება 30–60 წუთში.
4. **ხილული ბანერი** — ორივე მხარეს ჩანს, რომ სესია იმპერსონირებულია.
5. **მოქმედებების შეზღუდვა** — impersonation-ის დროს დაბლოკილია: წაშლა, მასობრივი ექსპორტი, ბილინგის ცვლილება, სამედიცინო ჩანაწერების ნახვა.
6. **სრული აუდიტი** — ყოველი მოქმედება ინახება `on_behalf_of` მარკერით.
7. **შეტყობინება Owner-ს** — email/notification სესიის დაწყებისას.

## 7.2. Break-glass (`SUPER_ADMIN`-ის სრული წვდომა)

`SUPER_ADMIN`-ს **ყველაფერი შეუძლია** — მათ შორის ორგანიზაციის impersonation-ბლოკის გვერდის ავლა და სამედიცინო ჩანაწერების ნახვა. მაგრამ სენსიტიურ მონაცემებზე წვდომა არ ხდება ჩვეულებრივი ღილაკით, არამედ ცალკე, ცხადი პროცედურით.

**რას ნიშნავს პრაქტიკულად:**

| ნაბიჯი | დეტალი |
|---|---|
| 1. აქტივაცია | ცალკე ღილაკი "Break-glass access" — არა ჩვეულებრივი ნავიგაცია |
| 2. მიზეზი | სავალდებულო ტექსტი + ticket/case ID |
| 3. ხელახალი ავთენტიფიკაცია | პაროლი + 2FA აქ და ახლა (სესიის ასაკის მიუხედავად) |
| 4. ვადა | სესია ავტომატურად იწურება 60 წუთში, გახანგრძლივება = ახალი მიზეზი |
| 5. ხილვადობა | მუდმივი წითელი ბანერი ეკრანზე |
| 6. აუდიტი | ყოველი **წაკითხვაც** ჩაიწერება, არა მხოლოდ ცვლილება |
| 7. შეტყობინება | Owner-ს ეგზავნება notification (შესაძლოა გადავადებით, თუ მიმდინარეობს შიდა გამოძიება) |

**რატომ ღირს ეს დამატებითი ხახუნი:**

- **დაცვა ბრალდებისგან.** მონაცემის გაჟონვისას პირველი კითხვა იქნება "Bookpitch-ს ხომ არ ჰქონდა წვდომა?" — ჟურნალით პასუხობ ზუსტად. მის გარეშე უდანაშაულობას ვერ ამტკიცებ.
- **გაყიდვების არგუმენტი.** მსხვილი კლინიკა კონტრაქტში მოითხოვს "თქვენს თანამშრომლებს ჩვენს მონაცემებზე თანხმობის გარეშე წვდომა არ უნდა ჰქონდეთ". თუ პასუხია "შეზღუდვა ტექნიკურად შეუძლებელია" — გარიგება ჩავარდა.
- **Blast radius.** `SUPER_ADMIN` პლატფორმის #1 სამიზნეა. ერთი წარმატებული ფიშინგი არ უნდა უდრიდეს ყველა კლინიკის პაციენტების ბაზას.

### ოპერაციული წესი: root account pattern

AWS-ის root ანგარიშის ლოგიკა — **როლს სრული ძალაუფლება აქვს, მაგრამ ყოველდღიური სამუშაო მასზე არ კეთდება:**

- იმავე ადამიანებს ცალკე `PLATFORM_ADMIN` ანგარიში აქვთ ყოველდღიური მუშაობისთვის
- `SUPER_ADMIN`-ის ყოველი login-ი აგზავნის alert-ს (Slack/email)

## 8. სამართლებრივი კონტექსტი (საქართველო)

თუ პლატფორმაზე კლინიკები არიან, ეს არ არის მხოლოდ ტექნიკური საკითხი.

- პერსონალურ მონაცემთა დაცვის ახალი კანონი ძალაშია **2024 წლის 1 მარტიდან** და ევროპულ (GDPR) სტანდარტებთანაა დაახლოებული.
- **ჯანმრთელობის მონაცემი განსაკუთრებული კატეგორიაა** და დამატებით დაცვას საჭიროებს — ე.ი. სამედიცინო ჩანაწერზე წვდომა უნდა იყოს ვიწრო, დასაბუთებული და ჟურნალირებული.
- **სამედიცინო დაწესებულებები ვალდებულნი არიან დანიშნონ პერსონალურ მონაცემთა დაცვის ოფიცერი** — ე.ი. შენი კლიენტები აუცილებლად გკითხავენ, როგორ არის ეს მოწესრიგებული. ეს გაყიდვების არგუმენტიც არის.
- Bookpitch იურიდიულად, სავარაუდოდ, **უფლებამოსილი პირია (processor)**, კლინიკა კი **პასუხისმგებელი პირი (controller)**. ეს კონკრეტულ სახელშეკრულებო ვალდებულებებს ნიშნავს.
- დიდი მოცულობის განსაკუთრებული კატეგორიის დამუშავებისას შესაძლოა საჭირო გახდეს **გავლენის შეფასება (DPIA)**.

**რას ნიშნავს ეს პრაქტიკულად:**
- ✅ default-deny კლინიკურ მონაცემებზე `PLATFORM_ADMIN`-ისა და `SUPPORT_AGENT`-ისთვის; `SUPER_ADMIN`-ისთვის — break-glass
- ✅ აუდიტ-ლოგი ყოველი კლინიკური ჩანაწერის **წაკითხვაზეც**, არა მხოლოდ ჩაწერაზე
- ✅ აუდიტ-ლოგი append-only, წაშლის შესაძლებლობის გარეშე
- ✅ soft-delete + ანონიმიზაცია, არა hard-delete (7-სამუშაო-დღიანი ვადა თანხმობის გაუქმებაზე)
- ✅ per-organization data export ("გადამტანობის უფლება")
- ✅ Postgres RLS ან ეკვივალენტი — tenant isolation მხოლოდ აპლიკაციის დონეზე არ დაამყარო

> ეს ზოგადი ორიენტირია და არა იურიდიული რჩევა — ფინალურ დიზაინამდე ღირს იურისტთან გადამოწმება.

## 10. ავტორიზაციის შემოწმება

```ts
// ტოკენში: user_id + active_organization_id + membership_id + permissions_version
// permissions ქეშირდება Redis-ში, ინვალიდირდება version-ის ცვლილებაზე

function can(ctx: AuthContext, permission: string, resource?: Resource): boolean {
  // 1. Platform plane — არ ეხება ორგანიზაციის მონაცემებს
  if (permission.startsWith('platform.')) {
    return ctx.platformPermissions.has(permission);
  }

  // 2. Tenant isolation — ჯერ ეს, მერე ყველაფერი
  if (resource && resource.organizationId !== ctx.activeOrganizationId) {
    return false;                       // ← ყველაზე მნიშვნელოვანი ხაზი
  }

  // 3. Impersonation-ის შეზღუდვები
  if (ctx.isImpersonating && RESTRICTED_DURING_IMPERSONATION.has(permission)) {
    return false;
  }

  // 4. სქოუფის შემოწმება
  const granted = ctx.permissions;      // membership-იდან

  if (granted.has(`${permission}:org`)) return true;

  if (granted.has(`${permission}:branch`)) {
    return ctx.branchIds.includes(resource?.branchId);
  }

  if (granted.has(`${permission}:own`)) {
    return resource?.ownerUserId === ctx.userId;
  }

  return granted.has(permission);       // სქოუფის გარეშე
}
```

**ორი ფენა თავდაცვისთვის:**
1. აპლიკაციის დონე — `can()` ყოველ endpoint-ზე (middleware/policy)
2. მონაცემთა ბაზის დონე — Postgres RLS `organization_id`-ზე

მხოლოდ პირველი საკმარისი არ არის: ერთი დავიწყებული `where` და გაქვს cross-tenant გაჟონვა.

## 13. მოკლე შეჯამება

1. **ორი სიბრტყე** — პლატფორმის როლი ≠ ორგანიზაციის როლი, ისინი ერთ ჯაჭვში არ დგანან
2. **`memberships`, არა `users.role`** — ეს ერთი გადაწყვეტილება ხსნის სოლო პრაქტიკოსს, მრავალ-ორგანიზაციის ექიმს და ფილიალებს
3. **Owner ≠ Admin** — ბილინგი და წაშლა მხოლოდ Owner-თან
4. **ნებართვები = მონაცემი** — custom როლები მოგვიანებით უმტკივნეულოდ დაემატება
5. **`SUPER_ADMIN`-ს ჭერი არ აქვს, სუპორტს — აქვს.** სენსიტიურ მონაცემებზე წვდომა break-glass-ით; აუდიტ-ლოგი append-only, ყველასთვის
6. **Tenant isolation ბაზის დონეზეც** — RLS, არა მხოლოდ აპლიკაციური `where`
7. **ვერტიკალ-ნეიტრალური სახელები** — Provider/Client/Service, არა Doctor/Patient/Procedure
