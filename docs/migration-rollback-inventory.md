# Migration rollback inventory

**As of 2026-10-18, on `main` (`fdf6559`): 74 migrations. 37 have a rollback written down, and none of them deletes its ledger row.**

This is the record for the migrations that are already applied, which must not
be edited (Prisma records their checksums). New migrations are held to a rule
instead: `tests/migration-rollback-docs.test.ts`, below.

## The rule for every rollback

1. **Delete the ledger row in the same transaction.** Dropping a migration's
   objects leaves its `_prisma_migrations` row saying "applied". The next
   `prisma migrate deploy` then reports "No pending migrations", and the
   objects stay gone for good, visible only to whichever invariant check
   happens to cover them.

   ```sql
   BEGIN;
   -- the migration's own reverse statements, then:
   DELETE FROM _prisma_migrations WHERE migration_name = '<the migration>';
   COMMIT;
   ```

   `prisma migrate resolve --rolled-back` is **not** a substitute: Prisma refuses
   it for a migration that succeeded (P3012, measured 2026-10-17). It is the right
   command only for a migration that **failed** mid-apply, which Prisma records
   as failed and which blocks every later deploy (P3009) until resolved.
2. **Revert the pull request too.** While the migration file is still in the
   repository with no ledger row, the next `migrate.yml` run (any push to
   `main` touching `prisma/migrations/**`) re-applies it.
3. **Prefer a forward fix.** Migrations here are expand-only. A new migration
   that undoes the effect is reviewable, tested and recorded. A hand-run rollback
   is none of those.
4. **Take the recovery point first.** Before any production rollback, confirm a
   recent green `production-backup.yml` run (`docs/operations.md` §3). For
   data, the backup is the only recovery point there is (no PITR).

## What a rollback cannot undo

| Kind | Migrations | What that means |
|---|---|---|
| Writes rows when applied | 14 | Backfills, seed and reference data, bootstrap credentials, permission revocations. Reversing the DDL does not reverse the data. Data written since is not reconstructed by any written rollback; the backup is the recovery point. **Do not "roll back" a credential or permission migration by re-running an earlier one**: `20260812000002_neutralize_bootstrap_credential` exists precisely so the bootstrap credential cannot come back |
| Destructive | 2 | `20260723000008_audit_partition` copied `audit_log` into the partitioned table and dropped `audit_log_legacy`. `20260806000003_reauth_session_purpose_binding` dropped `platform_reauth_grant`. Recoverable only from a backup taken before them |
| Creates or alters roles | 2 | Roles are cluster globals: a database restore does not bring them back, and a rollback must never drop `bookpitch_app` (the runtime role, invariant check 2) |
| Adds an enum value | 1 | `20260915000001_message_state_skipped`. PostgreSQL cannot drop an enum value in one statement. Leave it, since an unused value is harmless. Recreating the type is a migration of its own |
| Installs code that writes rows | 2 | `20260728000100_rbac_sync_triggers`, `20260813000001_sync_owner_user_id`. Dropping a trigger stops future writes and leaves past ones |
| Additive DDL only | the rest | Reversed by dropping what was added (plus the ledger row). **Anything written into the new objects since is lost with them** |

## The rule for new migrations

`tests/migration-rollback-docs.test.ts` applies to every migration from
`20261017000000` on. It reads the `ROLLBACK` section, meaning the heading comment
and the contiguous comment block under it, and requires:

1. one transaction in it, `BEGIN; … COMMIT;`;
2. inside that transaction, the migration's **own** ledger delete
   (`DELETE FROM _prisma_migrations WHERE migration_name = '<its name>'`), so the
   objects and the ledger row go together or not at all;
3. inside it too, at least one step that changes the schema or the data:
   `DROP`, `ALTER`, `CREATE`, `GRANT`, `REVOKE`, `TRUNCATE`, `COMMENT ON`,
   `DELETE`, `INSERT`, `UPDATE`, or a `DO` block whose body does. `SELECT 1;` is
   not a reverse (Codex review on #124, 2026-10-28). Whether the step reverses
   *this* migration is still for review, and for an executable rollback proof
   on a disposable copy, as #112's doc records;
4. no other SQL in the section: no second transaction, and no statement before
   the `BEGIN` or after the `COMMIT`. A step outside the transaction runs on its
   own, and if it fails after the ledger row is gone the rollback is partial.
   Statements are recognised line by line, by an SQL verb in capitals and its
   object, so prose around the transaction is free;
5. no executable SQL in the migration that touches `_prisma_migrations`.

The complements prove that each of these is reported:
- a missing section;
- `ROLLBACK: unavailable` plus a delete quoted in some other comment (Codex
  review on #124: the first version matched the delete anywhere in the
  comments);
- a delete placed after the `COMMIT`;
- a delete naming another migration;
- a transaction that only deletes the ledger row, or adds a step that changes
  nothing (`SELECT 1;`, `SET …`, a `DO` block that only reads);
- a second transaction after the first (Codex review on #124, 2026-10-24: the
  second version checked only the first transaction);
- a reverse step before the `BEGIN`, and one after a line of prose;
- an executable ledger write.

A complete rollback whose ledger step spans two lines passes, and so does prose
after the `COMMIT` that has semicolons and capitals in it.

The first migration it applies to is `20261017000001_practitioner_double_booking`
(#112), whose header was written to this rule.
